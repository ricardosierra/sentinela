domain/CallDecision.kt — variantes: `Allow`, `Silence`, `Reject`, `SendSilentlyToVoicemail`,
`BlockWithoutTrace`, todas carregando um `DecisionReason`.

domain/ScreenedCall.kt:
```kotlin
data class ScreenedCall(val direction: CallDirection, val number: ScreenedNumber)
enum class CallDirection { INCOMING, OUTGOING }
sealed interface ScreenedNumber {
    data class Valid(val e164: String) : ScreenedNumber
    data object Private : ScreenedNumber
    data object Invalid : ScreenedNumber
}
```

phone/PhoneNumberNormalizer — `normalize(raw: String, region: String? = null)` devolve um
resultado com a chave E.164 ou a marcacao de invalido. Conferir a assinatura exata no arquivo
antes de usar; e a mesma ja usada por `DefaultContactLookupRepository`.

Tabela de traducao FINAL (fonte AOSP, medida na pesquisa nos SDKs 29/33/34/35):
| CallDecision | CallResponse |
| Allow | `Builder().build()` — todos os campos false |
| Silence | `setSilenceCall(true)` e **nada mais** (qualquer outro campo lanca) |
| Reject | `disallow` + `reject` + `skipNotification` (+ `skipCallLog` conforme configuracao) |
| SendSilentlyToVoicemail | `disallow` + `reject` + `skipNotification` (identica a Reject na API) |
| BlockWithoutTrace | `disallow` + `reject` + `skipCallLog(true)` + `skipNotification(true)` |

Validacao real do construtor privado (lanca `IllegalStateException`):
`if (!shouldDisallowCall && (shouldRejectCall || shouldSkipCallLog || shouldSkipNotification))`.
Alem disso: `silenceCall` combinado com `rejectCall` ou `skipNotification` tambem lanca, e
`disallowCall + silenceCall` e legal mas ENGANOSO (o Telecom testa disallow primeiro e ignora o
silence) — **proibido**.

Campos garantidos de `Call.Details` (todo o resto vem em default/null e ler e bug latente):
`getCallDirection()`, `getCallerNumberVerificationStatus()`, `getConnectTimeMillis()`,
`getCreationTimeMillis()`, `getHandle()`. So chegam handles com scheme `tel:`.
