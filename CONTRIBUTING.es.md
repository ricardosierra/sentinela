# Guía de Contribución - Sentinela

¡Gracias por tu interés en contribuir a Sentinela! Esta guía establece las reglas básicas para asegurar que el proyecto mantenga su calidad, arquitectura y los estrictos estándares de privacidad propuestos por **SierraTecnologia** y **RicaSoluções**.

## 1. Código de Conducta

- Sé respetuoso en los issues y pull requests.
- El núcleo de este proyecto es la privacidad absoluta y la usabilidad. Las características que violen estos principios serán rechazadas sumariamente.

## 2. Estándares de Privacidad y Reglas de Oro

Sentinela es 100% offline y tiene una política estricta sobre los datos del usuario:
- **Cero Internet**: El permiso `android.permission.INTERNET` nunca debe ser añadido al Manifest del MVP.
- **Sin Registros Sensibles**: Nunca registres números de teléfono completos, nombres de contactos o fotos (`Log.d`, `println`, reportes de fallos). Utiliza máscaras o registros genéricos.
- **Almacenamiento Seguro**: No persistas información de la libreta de contactos (`ContactsContract`) en la base de datos. Los accesos deben ocurrir en tiempo real y solo en la memoria.

## 3. Arquitectura

Por favor, sigue las directrices en [`docs/ARQUITETURA.md`](docs/ARQUITETURA.md) (en portugués):
- **Motor de Decisión (Dominio)**: `CallDecisionEngine` y todo el paquete `domain/` deben ser Kotlin puro, sin dependencias del SDK de Android.
- **Inyección de Dependencias**: El MVP utiliza inyección de dependencias manual (vía `AppContainer`). Evita introducir frameworks pesados (como Hilt/Dagger) que puedan retrasar el *cold start* del `CallScreeningService`.
- **UI**: Todas las interfaces están construidas con Jetpack Compose usando Material 3. Ninguna cadena (string) escrita de forma fija en el código; todo debe pasar por `strings.xml`.

## 4. Configuración del Entorno y Pruebas

- El proyecto utiliza **AGP 9.3** y requiere **JDK 17**. No fuerces actualizaciones de bibliotecas sin consultar a los mantenedores.
- Antes de enviar un PR, asegúrate de que todo pase:
  ```bash
  ./gradlew testDebugUnitTest       # Pruebas unitarias
  ./gradlew lint detekt             # Análisis de calidad de código
  bash scripts/verify-invariants.sh # Verificaciones de integridad arquitectónica
  ```
- Exigimos un 80%+ de cobertura de código en los paquetes de dominio y telefonía.
- Esos mismos comandos se ejecutan solos en cada push y cada pull request, mediante el flujo de
  trabajo [`ci.yml`](.github/workflows/ci.yml) — ejecutarlos localmente adelanta el resultado, no
  lo sustituye. Cada ejecución adjunta los informes de detekt, lint, pruebas y cobertura. En una
  pull request la cobertura se **mide y se publica, no se reprueba**; la verificación del 80%
  (`koverVerify`) se aplica en la ruta de publicación, que llama a esa misma CI antes de firmar
  nada.

## 5. Estándares de Commits

Sigue los **Conventional Commits**:
- `feat:` para nuevas funcionalidades
- `fix:` para corrección de errores
- `docs:` para cambios en la documentación
- `refactor:` para cambios en el código que no alteran el comportamiento
- `test:` para añadir pruebas faltantes

Ejemplo:
`feat(ui): añade soporte de modo oscuro a la pantalla principal`

Nunca uses atribución artificial (`Generated by AI`, `Co-authored by Claude`). Firma con el nombre real del desarrollador.
