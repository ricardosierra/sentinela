# Guia de Contribuição - Sentinela

Obrigado por seu interesse em contribuir com o Sentinela! Este guia estabelece as regras básicas para garantir que o projeto mantenha sua qualidade, arquitetura e os rigorosos padrões de privacidade propostos por **SierraTecnologia** e **RicaSoluções**.

## 1. Código de Conduta

- Seja respeitoso nas issues e pull requests.
- O foco do projeto é privacidade absoluta e usabilidade. Recursos que violem esses princípios serão rejeitados sumariamente.

## 2. Padrões de Privacidade e Regras de Ouro

O Sentinela é 100% offline e tem uma política estrita sobre dados de usuários:
- **Zero Internet**: A permissão `android.permission.INTERNET` nunca deve ser adicionada ao Manifest do MVP.
- **Nenhum log sensível**: Nunca grave números de telefone completos, nomes de contatos ou fotos no log (`Log.d`, `println`, `Crashlytics`, etc.). Use máscaras ou logs genéricos.
- **Armazenamento Seguro**: Não persista informações da agenda telefônica (`ContactsContract`) no banco de dados. Os acessos devem ocorrer em tempo real e apenas na memória.

## 3. Arquitetura

Siga as orientações em [`docs/ARQUITETURA.md`](docs/ARQUITETURA.md):
- **Motor de Decisão (Domain)**: `CallDecisionEngine` e todo o pacote `domain/` devem ser Kotlin puro, sem dependências do SDK do Android.
- **Injeção de Dependência**: O MVP utiliza injeção de dependência manual (via `AppContainer`). Evite a introdução de frameworks pesados (como Hilt/Dagger) que possam atrasar o *cold start* do `CallScreeningService`.
- **UI**: Toda a interface é escrita em Jetpack Compose usando Material 3. Nenhuma string hardcoded; todas devem estar em `strings.xml`.

## 4. Configuração do Ambiente e Testes

- O projeto utiliza **AGP 9.3** e exige **JDK 17**. Não force atualizações de bibliotecas sem consultar os mantenedores.
- Antes de submeter um PR, verifique se tudo passa:
  ```bash
  ./gradlew testDebugUnitTest       # Testes unitários
  ./gradlew lint detekt             # Análise de qualidade de código
  bash scripts/verify-invariants.sh # Scripts de integridade arquitetural
  ```
- Exigimos 80%+ de cobertura de código no pacote de domínio e telefonia.
- Esses mesmos comandos rodam sozinhos em toda push e toda pull request, pelo workflow
  [`ci.yml`](.github/workflows/ci.yml) — rodar localmente antecipa o resultado, não o substitui.
  Cada execução anexa os relatórios de detekt, lint, testes e cobertura. Em pull request a
  cobertura é **medida e publicada, não reprovada**; o gate de 80% (`koverVerify`) é aplicado no
  caminho de publicação, que chama essa mesma CI antes de assinar qualquer coisa.

## 5. Padrão de Commits

Siga o **Conventional Commits**:
- `feat:` para novas funcionalidades
- `fix:` para correções de bugs
- `docs:` para mudanças em documentação
- `refactor:` para mudanças de código sem impacto no comportamento
- `test:` para adição de testes

Exemplo:
`feat(ui): adiciona suporte ao modo noturno na tela principal`

Nunca utilize autoria artificial (`Generated by AI`, `Co-authored by Claude`). Assine com o nome do desenvolvedor.
