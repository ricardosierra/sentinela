# Contributing Guide - Sentinela

Thank you for your interest in contributing to Sentinela! This guide establishes the basic rules to ensure the project maintains its quality, architecture, and the strict privacy standards proposed by **SierraTecnologia** and **RicaSoluções**.

## 1. Code of Conduct

- Be respectful in issues and pull requests.
- The core of this project is absolute privacy and usability. Features that violate these principles will be outright rejected.

## 2. Privacy Standards & Golden Rules

Sentinela is 100% offline and has a strict policy regarding user data:
- **Zero Internet**: The `android.permission.INTERNET` permission must never be added to the MVP's Manifest.
- **No Sensitive Logs**: Never log full phone numbers, contact names, or photos (`Log.d`, `println`, crash reporters). Use masked or generic logs.
- **Secure Storage**: Do not persist phonebook data (`ContactsContract`) in the local database. Access must occur in real-time and remain strictly in memory.

## 3. Architecture

Please follow the guidelines in [`docs/ARQUITETURA.md`](docs/ARQUITETURA.md) (in Portuguese):
- **Decision Engine (Domain)**: `CallDecisionEngine` and the entire `domain/` package must be pure Kotlin, with zero Android SDK dependencies.
- **Dependency Injection**: The MVP uses manual DI (via `AppContainer`). Avoid introducing heavy frameworks (like Hilt/Dagger) that could delay the `CallScreeningService`'s cold start.
- **UI**: All interfaces are built with Jetpack Compose using Material 3. No hardcoded strings; everything must go through `strings.xml`.

## 4. Environment Setup and Testing

- The project uses **AGP 9.3** and requires **JDK 17**. Do not force library updates without consulting the maintainers.
- Before submitting a PR, ensure everything passes:
  ```bash
  ./gradlew testDebugUnitTest       # Unit tests
  ./gradlew lint detekt             # Code quality analysis
  bash scripts/verify-invariants.sh # Architectural integrity checks
  ```
- We require 80%+ code coverage on the domain and telephony packages.
- These same commands run on their own for every push and every pull request, via the
  [`ci.yml`](.github/workflows/ci.yml) workflow — running them locally gets you the answer
  sooner, it does not replace CI. Every run attaches the detekt, lint, test and coverage
  reports. On a pull request coverage is **measured and published, not failed**; the 80% gate
  (`koverVerify`) is applied on the release path, which calls this same CI before signing
  anything.

## 5. Commit Standards

Follow **Conventional Commits**:
- `feat:` for new features
- `fix:` for bug fixes
- `docs:` for documentation changes
- `refactor:` for code changes that do not alter behavior
- `test:` for adding missing tests

Example:
`feat(ui): add dark mode support to the main screen`

Never use artificial attribution (`Generated by AI`, `Co-authored by Claude`). Sign off with the actual developer's name.
